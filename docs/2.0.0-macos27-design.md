# macOS 27 look and feel, and what it means for PrismPack

Written 29 Oct 2026 for the 2.0 GUI. The mockups in
[2.0.0-mockups.html](2.0.0-mockups.html) are being brought in line with this.

**How much to trust this.** The facts below come from three kinds of source,
marked on each line:

- **[Apple]**: Apple's own pages, or the macOS 27 SDK on this Mac (version
  27.0, headers and Swift interfaces). Most reliable.
- **[Press]**: news and blog coverage of the WWDC 2026 keynote and the betas.
  Good for what changed, weaker on exact details.
- **[Mine]**: my judgement for PrismPack. Not a fact about macOS.

I could not see macOS 27 screenshots or run its UI, so nothing here is checked
against pixels. Every layout number in the mockup is an estimate until the real
SwiftUI build runs on this Mac.

## 1. What changed from macOS 26 (Tahoe) to 27 (Golden Gate)

| Area | macOS 27 | Source |
|---|---|---|
| **Sidebars** | **No longer float.** They run edge to edge, from the top of the window to the bottom, and no longer cast a shadow. Liquid Glass refraction continues underneath them instead of stopping at the sidebar edge. | Press (MacRumors, Michael Tsai's roundup) |
| **Sidebar icons** | **Coloured again**, after Tahoe's monochrome grey. Apple's sidebar guidance was updated on 8 June 2026 for this. By default they use the app's accent colour and follow the user's chosen system accent colour. Fixed colours are fine if used sparingly, to mean something (Mail's yellow VIP icon). | Apple (HIG change log), Press |
| **Active window** | The active window's sidebar is darkened, and colour icons appear only in the frontmost window. Shadows changed to make the active window easier to tell. | Press (one review) |
| **Toolbars** | One uniform toolbar across the top of each window. Clear dividers are back. Buttons sit on a faint bar, which one critic dislikes. | Press |
| **Window corners** | Every window has the **same** corner radius, and it is **less round** than Tahoe's. Intel Macs reportedly stay on the old look. | Press |
| **Liquid Glass slider** | New in System Settings, Appearance: from clearer to more opaque and tinted. It reaches menus, Control Center, Spotlight, toolbars and sidebars, but not the menu bar, Dock or Finder icons. Reviewers call the effect subtle. Reduce Transparency still makes sidebars and toolbars opaque. | Press |
| **Glass rendering** | Default glass was retuned for contrast and vibrancy. A darker edge and brighter highlights separate layers. | Press (MacRumors) |
| **Menu item icons** | Hidden by default in menu bar and context menus. Apple keeps a few (Settings, Share, Print). Applies to apps linked against the 26.0 SDK or later. | Apple (release notes, `NSMenuItem.h`) |
| **App icons** | More Liquid Glass layers, crisper in light, dark, tinted and clear modes. Mac icons keep the squircle shape. | Press |
| **Other** | HDR is used for depth. Settings no longer uses progressive blur at scroll edges. Spotlight rebuilt around "Search or Ask". | Press |

## 2. What the macOS 27 SDK on this Mac confirms

Checked in `/Applications/Xcode.app/.../MacOSX.sdk` (SDK 27.0):

- `NSMenuItem.preferredImageVisibility` is **macOS 27 only**. The header says
  AppKit decides menu image visibility and "will typically hide images". Use
  `.visible` to force one.
- New in AppKit 27: **per-view corner configuration**
  (`NSViewCornerConfiguration`, `NSViewCornerRadii`, `effectiveCornerRadii`,
  `viewDidChangeEffectiveCornerRadii`). This is how views can match the shared
  window radius instead of hard-coding one.
- `NSGlassEffectView.effectIsInteractive` is new in 27, and
  `NSToolbarItemGroup` gained a `role`.
- SwiftUI still has `backgroundExtensionEffect()` (the "mirror content under the
  sidebar" effect from Apple's guidance), `NavigationSplitView`, and
  `toolbarBackgroundVisibility`.
- I found **no** new SwiftUI API named for the sidebar change. It most likely
  comes from the system styling of `NavigationSplitView` and `List` with the
  sidebar style, so using the standard controls gets the 27 look for free. I
  did not confirm this by running one.

## 3. What Apple's sidebar guidance says (updated 8 June 2026)

From Apple's Human Interface Guidelines, Sidebars page:

- Let people hide and show the sidebar, with a button or Show/Hide Sidebar
  commands in the View menu. Do not hide it by default.
- Show **no more than two levels** of hierarchy. Use disclosure controls to keep
  it short.
- Use SF Symbols for items. Make sure any fixed icon colour has a clear purpose,
  and honour the user's accent colour.
- Row height, text and glyph size depend on the sidebar size (small, medium,
  large), which people change in System Settings, General. Support it.
- **Avoid critical information or actions at the bottom of a sidebar.** People
  move windows so the bottom edge is hidden.
- Let people customise the sidebar's contents when you can.
- Consider auto-collapsing the sidebar when the window gets narrow.

## 4. What this means for PrismPack

**Sidebar**
- Edge to edge: full window height, flush to the left and bottom, no inset, no
  rounded outer card, no shadow. A thin separator or the glass edge divides it
  from the content.
- Coloured icons. Use the system accent colour by default and keep fixed
  colours for meaning only. My earlier idea of a different colour on every
  nav item would fight the guidance, so I'm limiting colour to the **section
  colours inside the Updates list** and using the accent colour for nav icons.
- Header: app icon, **PrismPack**, and "Version 2.0.0" at the **top**. The top
  is safe. The version must not live at the bottom.
- Collapse button: HIG says to offer one but not where. In 27 the toolbar is
  unified, so the natural spot is the leading end of the toolbar rather than
  inside the sidebar. **Unverified.** The SwiftUI `NavigationSplitView` adds its
  own toggle, which is the safest choice.
- Items: Updates, Discover, Installed, Activity, Settings. One level, so no
  disclosure needed.
- Support the system sidebar icon size setting by using standard `Label` rows
  and not fixed pixel sizes.

**Toolbar**
- One uniform toolbar across the top. The page title, "Check now" and "Update
  all" belong there, with a clear divider below it.

**Windows**
- Don't hard-code a corner radius on the window or on big containers. Use the
  corner configuration API (macOS 27) and keep a sensible default for macOS 26.
- Section cards keep their own smaller radius, concentric with the window.

**Glass**
- Keep Liquid Glass for the section cards and controls, tinted per section
  colour. Don't stack glass on glass, and do not tint the whole window.
- **Open decision: today's in-app "Glass" slider.** macOS 27 now has a system
  slider that does a similar job. Two sliders that do nearly the same thing will
  confuse people. [Mine] Recommend keeping the in-app Theme picker but dropping
  the Glass slider on macOS 27, and following the system setting. The
  slider stays on macOS 26.

**Menus**
- Do not rely on icons in menus. Mac menus hide them by default now. Use plain
  text items and add `preferredImageVisibility = .visible` only for the rare
  case where the icon carries meaning.

**App icon**
- The new icon should be an Icon Composer file with separate layers so it gets
  the 27 depth in light, dark, tinted and clear. Build step: the project already
  compiles `Resources/AppIcon.icon` with `actool` and stamps the linked SDK
  version in `build-app.sh`, so a new icon drops in the same way.

**Contrast and accessibility**
- Test every section tint with the system slider at both ends and with Reduce
  Transparency on. Section headers and row text must stay readable on the tint.

## 5. Things to verify once it runs

1. Whether the standard `NavigationSplitView` sidebar already renders edge to

2. Where macOS 27 puts the sidebar toggle in a unified toolbar.
3. The exact window corner radius, and whether `effectiveCornerRadii` returns it.
4. How the section tints look with the glass slider at clear and at opaque.
5. Whether colour sidebar icons appear only in the frontmost window, as one
