# Renaming UpdateScout to PrismPack: migration plan

Written 28 Oct 2026 on `release/2.0.0`. **This is a plan only. No code has
changed, and nothing has been pushed, tagged or released.** It follows the
decisions in [2.0.0-vision.md](2.0.0-vision.md) and the rename section of
[2.0.0-plan.md](2.0.0-plan.md).

## 1. Summary

- **Goal:** 2.0 ships as **PrismPack**. Everyone on 1.8.0 gets it through
  Sparkle, keeps their data and settings, and keeps background checks working.
- **The one thing that can break it:** Sparkle behaviour when the app's name
  (and possibly its bundle ID) changes. I haven't verified how Sparkle 2.8
  treats either, so **step 0 is a local rehearsal** before any real work.
- **Recommendation: change the brand, keep the plumbing.** Rename everything
  users see, but keep the bundle ID `com.nickszun.updatescout`, the launchd
  label, and the data folder for 2.0. That removes most of the risk. A full
  rename (Plan B below) stays available as a fallback and as a later step.
- **The name isn't the old name's problem alone.** Another paid Mac app is
  already called UpdateScout (`updatescout.gumroad.com`), so renaming also ends
  that clash.

## 2. What the rename touches

Found by searching the repo. Line numbers are from today's tree.

| Preferences | `Store.swift`, `App.swift`, `HomebrewSource.swift`, `UpdatesWindow.swift` | UserDefaults in the bundle ID's domain: `disabledSources`, `checkIntervalMinutes`, `showDockIcon`, `appearance`, `didFirstRunSetup`, `lastBrewUpdate`, `collapsedSections`, `showHidden` |

Two facts from this table drive the plan:

1. **`SUFeedURL` and `SUPublicEDKey` are baked into every 1.x build.** Those
   builds will look at the old feed URL and trust only the old key for as long
   as they exist. The 2.0 item must appear in **that** feed, signed by **that**
   key.
2. **The release script pushes `main` before creating the GitHub release**, as
   CLAUDE.md warns. A failed push would leave a half-finished release, so check
   push access first.

## 3. Step 0: rehearse the update locally (do this first)

Goal: learn, without publishing anything, what Sparkle does when a build is
renamed. Questions to answer:

- Does Sparkle accept an update whose **bundle name** changed?
- Does it rename `/Applications/UpdateScout.app` to `PrismPack.app`, or keep the
  old filename?
- Does it accept an update whose **bundle ID** changed? (Only needed for Plan B.)

How, entirely on this Mac:

1. Make a **throwaway Sparkle key pair** for the rehearsal. **Do not touch the
   real signing key.** It stays where it is, and Nick runs real signing.
2. Build an "old" test app: 1.8.0 code with the throwaway public key and a
   feed URL pointing at `http://localhost:<port>/appcast.xml`.
3. Build a "new" test app: the renamed build, signed with the throwaway key,
   with a higher build number.
4. Serve a test appcast from a local folder with `python3 -m http.server`.
5. Run the old build from a scratch folder, not `/Applications`, and let it
   update. Watch what lands where.

Rules from CLAUDE.md for test builds: **quit the installed copy first** (both
copies share the bundle ID and the data folder), and **never toggle "Check for
updates in the background"** in a test build, because that points the real
launchd agent at it.

The result decides between Plan A and Plan B and shapes the repair step in
section 6.

### 3.1 Rehearsal results (run 29 Oct 2026)

Run locally with a throwaway key, a localhost appcast and scratch copies of
the 1.8.0 code. The real key, the installed app and the real launch agent were
not touched. Each case started from the same old build (`com.rehearsal.scout`,
build 25) and offered a signed build 26.

| Case | New app's name | New bundle ID | Result |
|---|---|---|---|
| A | New (`PrismTestA.app`, new executable) | Same | **Installed.** Sparkle replaced the contents but kept the **old folder name** (`RehearseOld.app` now holds version 2.0.0 with the new executable). |
| B | New | Changed | **Rejected.** Sparkle logged "No suitable install is found in the update". The app stayed on 1.8.0. |
| C | **Old filename** | Changed | **Installed**, with the new ID, in the old folder name. |

What this means:

- Sparkle looks in the zip for an app with the old app's name, and falls back to
  one with the same bundle ID. If neither matches, it rejects the update.
- **Plan A works as written.** Rename the display name and executable freely
  and keep the ID. The installed copy stays `UpdateScout.app` on disk. If
  `PrismPack.app` is wanted in `/Applications`, the first launch has to offer
  to rename it (the app can move itself and repair the launch agent path).
- **Plan B needs the zip to contain `UpdateScout.app`**, not `PrismPack.app`,
  for the 1.8 to 2.0 hop. A bridge release is only needed if the app must also
  have the new filename after that hop.
- Caveats: the test builds were ad-hoc signed like the real app, an HTTP
  localhost feed was used rather than the GitHub raw URL, and Sparkle's
  automatic-install mode was used (install on quit). The manual "Install and
  Relaunch" path wasn't run, but it uses the same installer. Notification
  permission and the launch agent weren't exercised.
- Side finding: Sparkle in this app only starts when the Settings or Updates
  window is opened (`SelfUpdater.controller` is lazy). Automatic update checks
  therefore never run until the user opens one of those windows. Worth fixing
  in 2.0 by touching the controller at launch.

## 4. Plan A (recommended): new name, same plumbing

Change what users see. Keep what the system keys on.

| Area | Decision |
|---|---|
| **Bundle ID** | Keep `com.nickszun.updatescout`. Users never see it. Keeping it keeps notification permission, any granted privacy permissions, login item state and the preferences domain exactly as they are. |
| **Display and bundle name** | Change to `PrismPack`. |
| **App filename** | `PrismPack.app`. Sparkle does **not** rename an installed copy (rehearsal result below), so users keep `UpdateScout.app` on disk after the update. |
| **Launch agent** | Keep the label `com.nickszun.updatescout.check`. Add a **repair on first launch**: if the agent's plist points at a path that no longer exists, rewrite it to the app's real path and reload it. This is the same fix as the "launch agent stores the app's current path" item in `2.0.0-plan.md`. |
| **Data folder** | Keep `~/Library/Application Support/UpdateScout/` for 2.0. Nothing moves, so there is nothing to lose. Optionally rename it in a later release with a one-time copy and a symlink. |
| **Preferences** | Nothing moves, same domain. |
| **Sparkle** | Same feed URL, same key, new 2.0 item added to the existing appcast. |

**Why this is safer:** the whole migration risk sits in one place, whether
Sparkle handles the filename change. The data, preferences, permissions and the
background agent never change owner.

**Cost:** a legacy identifier stays in system-level places (`defaults`, the
launchd label). Nobody sees it in normal use.

## 5. Plan B (fallback): full rename including the bundle ID

Use this only if Nick wants a clean identifier, or if rehearsal shows Sparkle
handles a changed ID fine. Everything in Plan A, plus:

| Area | Decision |
|---|---|
| **Bundle ID** | `com.nickszun.prismpack`. macOS treats it as a different app: **notification permission resets**, privacy grants (for example Full Disk Access, if granted) must be given again, and the login item must be set up again. |
| **Launch agent** | New label `com.nickszun.prismpack.check`. On first launch: `launchctl bootout` the old label, delete the old plist, and, **only if the old agent was installed**, install the new one pointing at the new path. Keep the "enabled" state, not just the file. |
| **Data folder** | New `~/Library/Application Support/PrismPack/`. On first launch, **copy** (don't move) the old folder across. Do it under the same lock `Store.mutate` uses, because the app and the background agent both write `state.json`. Stop the old agent first so it can't write mid-copy. Leave the old folder for at least two releases so a rollback still works. |
| **Preferences** | Read the old domain once with `UserDefaults(suiteName: "com.nickszun.updatescout")`, copy the eight keys listed in section 2, then set a `migratedFromUpdateScout` marker so it never runs twice. |
| **`askpass.sh`** | Regenerated in the new folder. It's built at runtime, so nothing to carry over. |
| **Sparkle** | Same feed and key. Rehearsal result: a changed bundle ID **is accepted** only if the zip's app keeps the **old filename** (`UpdateScout.app`). With both changed, Sparkle rejects the update. See section 3.1. |

### Bridge release (needed for a new filename **and** a new ID)

A last 1.x build, say 1.9.0, keeps the old ID. When it runs it downloads
`PrismPack.app` itself, using the zip-install code the app already has for
other Sparkle apps (`SparkleInstaller.swift`), copies the data across, moves the
launch agent, and removes the old app. It's more work and more to test, which
is why Plan A is the recommendation.

## 6. Sparkle continuity: how 1.8 users get 2.0

The rules that must hold whichever plan is chosen:

1. **Same feed URL.** The 2.0 item goes into the **existing** `appcast.xml` at
   the existing raw URL.
2. **Same EdDSA key.** Never regenerate it. Existing users trust only that key.
   A new key would leave every 1.x install unable to update.
3. **A higher build number.** `CFBundleVersion` is 25 now. The 2.0 build must
   be higher, and `release.sh` already bumps it.
4. **The download URL can be anywhere.** The `enclosure` URL doesn't have to
   match the repo name, so the zip can be `PrismPack-2.0.0.zip` under whatever
   repo name is live at that moment.
5. **Betas don't reach 1.8 users.** Items tagged `sparkle:channel` beta are only
   shown to apps that allow that channel. 1.8 doesn't, so only people who run a
   beta build will see betas, which is what we want. (This also means testers
   need the beta build installed by hand the first time.)
6. **Keep the old feed alive forever.** Any 1.x install still asks the old URL.

### The GitHub repo name

Renaming `nickstar14/UpdateScout` to `nickstar14/PrismPack` is cosmetic.
GitHub redirects the old repository URLs, but I haven't confirmed that
`raw.githubusercontent.com` file URLs follow the redirect for a renamed repo.
That is the URL every 1.x build uses, so **don't rename the repo until it has
been verified**, and **never create a new repo called `UpdateScout`**, because
that would break the redirect.

Safest order: ship 2.0 with the repo unchanged, confirm everyone updates, then
rename the repo and re-verify the feed URL and download links.

## 7. First launch of 2.0

Both plans run a small one-time step on first launch:

1. **Repair the launch agent** if its stored path is stale (Plan A), or move it
   to the new label (Plan B).
2. **Show a short notice:** "UpdateScout is now PrismPack. Your settings and
   history carried over."
3. **Check** that the data loaded, that the ignored and notified lists are
   intact, and log it.

The item IDs include the install token. The rename doesn't touch that format,
so ignored and notified lists survive.

## 9. Verification checklist (all local)

Run these before anyone asks to publish.

- **Fresh install** of the renamed build works, and first-run setup runs.
- **Upgrade from a real 1.8.0 build** (the rehearsal setup): data, ignored and
  notified lists, custom sources and preferences are all still there.
- **Launch agent** is loaded with the right path:
  `launchctl print gui/$(id -u)/<label>` shows the new path, and
  `<app>/Contents/MacOS/<executable> --background-check` runs.
- **Moving the app** breaks nothing: the repair step fixes the agent.
- **Notifications** still arrive (Plan A), or the permission prompt appears once
  (Plan B).
- **The new build updates itself** to a later test build.
- **After a real publish (only on Nick's go-ahead):** the raw appcast URL lists
  2.0.0, the zip downloads, and the old repo URL still redirects.

## 10. Rollback

- Keep the 1.8.0 zip on the GitHub release page.
- The appcast item for 2.0 can be removed to stop new installs.
- Data is copied, never deleted, for two releases (Plan B), and untouched in
  Plan A.
- The launch agent change is reversible by reinstalling it from Settings.

## 11. Decisions for Nick

1. **Plan A or Plan B.** I recommend A, then decide after the rehearsal.
2. **Rename the repo** now, or after 2.0 has rolled out. I recommend after.
3. **Rename the data folder** at all, or leave `UpdateScout` in Application
   Support forever. I recommend leaving it for 2.0.
4. **Rename the Swift source folder** in the same release, or later. It makes
   a big diff but no behaviour change.
5. **Trademark and domain checks** on PrismPack before any public release.
