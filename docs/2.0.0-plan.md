# UpdateScout 2.0.0: handoff and plan

Written 28 Oct 2026, right after 1.8.0 shipped. This is everything from the
1.8.0 session that matters for 2.0: the original ideas, the code review, what
shipped, what was left over, and the decisions already made. Read it before
starting 2.0 work. Standing rules for working in this repo are in
[CLAUDE.md](../CLAUDE.md).

## Rename for 2.0

Nick suggested renaming for 2.0, since it's a much bigger app. Nothing is
decided yet.

- **"AppScout" is taken.** An iPhone app, "AppScout: App Metrics", is on the
  App Store and launched on Product Hunt in July 2026. An Android app, "AppScout:
  Find & Build Apps", uses the name too.
- **Check "UpdateScout" as well.** A web search turned up
  `updatescout.gumroad.com`. If that isn't Nick's, another product already uses
  the current name.
- **Each candidate name needs checking against:** the Mac App Store, the iOS
  App Store, Homebrew casks, GitHub, the domain, and a basic trademark search.
- **What a rename costs. Decide it first, before other 2.0 work:**
  - a new bundle ID (today `com.nickszun.updatescout`) and launchd label
    (`com.nickszun.updatescout.check`),
  - moving `~/Library/Application Support/UpdateScout/` and the user defaults to
    the new name on first launch,
  - removing the old launch agent and installing the new one,
  - Sparkle continuity: the last UpdateScout build must still find the update in
    the existing `appcast.xml` at the current URL, and keep the same EdDSA key.
    Otherwise existing users never get 2.0.
  - updating the GitHub repo name or adding a redirect, the release zip names,
    the app icon and the README.

## 2.0 features

These are Nick's ideas, plus the design notes from the 1.8.0 session.

### 1. Install queue rewrite (do this first)

Everything else on this list builds on it. Today:

- One global `cancelRequested` flag ([UpdateController.swift:166](../Sources/UpdateScout/UpdateController.swift:166)).
- One shared `"install"` process tag for every install.
- Install state is a string, with `"Queued…"` as a magic value (around
  line 174 and line 222).

Replace them with:

- an install-state enum (queued, downloading with a progress value,
  installing, needs admin, failed with an error, done),
- per-item cancel, with a process tag and a Task for each item.

### 2. Simultaneous updates (user-configurable)

- A concurrency setting, from 1 to about 8.
- Homebrew holds locks, so parallel `brew` calls can fail. Run downloads in
  parallel, but install one at a time per package manager. Sparkle and the
  App Store can run alongside Homebrew.
- A progress row for each item, with Cancel and Retry.

### 3. Single admin authorization and automatic updates (like UniGetUI)

- A GUI app can't reuse a `sudo -v` cache between runs, and `sudo -A` prompts
  on each call. So "Update All" can prompt several times today.
- Options, best first:
  - a privileged helper (SMAppService daemon) that the user approves once. This
    is the proper fix, but it needs signing and an XPC interface.
  - one elevated batch script per run, using `with administrator privileges`
    or one askpass session.
  - flagging the casks that need admin rights (`.pkg` installers) and running
    the rest without sudo.
- Auto-update:
  - global and per-app on/off, and a schedule (daily, on launch or weekly),
  - ignore a version, and pin an app,
  - never auto-install a major upgrade. That always goes through the review
    sheet.
  - Optional rules: "Wi-Fi only", "never update Xcode".

### 4. All-installed-apps view and per-app channel selection

- This needs a view of every installed app, not just the outdated ones. The
  Discover tab below needs the same data, so build them together.
- Channel support differs by source:
  - **Sparkle:** feasible. Feed items carry `sparkle:channel` tags, and the
    archive is still verified against the app's own key. Some feeds leave
    betas untagged (Thaw does), so keep the version-marker fallback from 1.8.0.
  - **Homebrew:** channels are separate casks (`firefox@nightly`,
    `thaw@beta`). Switching means uninstalling one and installing the other,
    and the two conflict, so handle it carefully.
  - **App Store:** there are no channels.
- Moving from beta back to stable is a downgrade. Normal comparison never
  offers it, so it needs its own action and a warning.
- **Opt-in cask conversion:** once the stable `thaw` cask passes an installed
  beta, the cask oracle could offer to convert a direct Sparkle install into a
  Homebrew one. For beta-track apps, make that opt-in.

### 5. Browse and search (Discover tab, like CaskHub)

- Use `brew search` and `brew info --json=v2 --cask` for names,
  descriptions, homepages and versions.
- formulae.brew.sh has install counts, which can drive a Popular list.
- Casks have no categories, so ship a bundled category mapping (Browsers,
  Developer, Media, Utilities and so on) that can be updated over time.
- Lists: Popular, Recently added and each category, with Install buttons.

### 6. Popover or straight to the window

The question: does the menu bar popover earn its click?

- If the popover keeps quick actions (Update All, the top few updates, Check
  Now, Quit), keep it.
- Otherwise add a setting: left-click opens the window, right-click shows the
  menu.

### Other ideas from the brainstorm (optional)

- Update history and rollback: a log of what changed and when, with release
  notes.
- Cleanup tools: `brew cleanup`, removing old versions, and showing the disk
  space freed.
- Actionable notifications ("3 updates ready – Update All").
- App Intents / Shortcuts ("Check for updates"), and a command-line mode.
- Menu bar extras: pause checks, and a launch-at-login setting.

## Leftover fixes from the 1.8.0 code review

These were found in the review but didn't ship in 1.8.0:

- **Launch agent:**
  - Settings shows "installed" when the plist file exists, not when the job is
    actually loaded.
  - The plist stores the app's current path, so moving the app breaks
    background checks without telling the user. Detect this and offer a repair.
- **App scanning** covers only the top level of `/Applications` and
  `~/Applications`. Apps in subfolders are missed.
- **Sparkle `sparkle:hardwareRequirements`** is ignored. Only
  `minimumSystemVersion` is honoured.
- **`softwareupdate` parsing** splits on commas, so titles that contain a comma
  break it ([SystemUpdateSource.swift:28](../Sources/UpdateScout/Sources/SystemUpdateSource.swift:28)).
- **The `.dmg` unpack** detaches the image in a fire-and-forget Task, so
  temp-folder cleanup can race the mounted volume
  ([SparkleInstaller.swift:225](../Sources/UpdateScout/SparkleInstaller.swift:225)).
- **No rollback:** the old app bundle is deleted with the temp folder once the
  swap succeeds. If the new version won't launch, there's nothing to go back
  to. Keeping it in the Trash would fix this.
- **Custom sources run their shell commands on every check,** including
  headless background checks. Consider an opt-in, or a separate "check
  command" for them.

## Things to verify early in 2.0

- **Menu bar managers.** The 1.8.0 icon was tested by eye with Thaw 3.0 beta,
  and Nick reported it looks good. Check again whenever the label changes:
  - one status item, never several,
  - the icon keeps its position through a check,
  - it renders correctly in Thaw's hidden-items bar.
- **MenuBarExtra labels drop view modifiers and SwiftUI animations.** Anything
  animated in the menu bar has to be pre-drawn frames, as
  [MenuBarIcon.swift](../Sources/UpdateScout/Views/MenuBarIcon.swift) does.
- **Thaw track behaviour:** when Thaw 3.0.0 final ships, check that 1.8.0+
  offers it to the installed 3.0.0-beta.x.

## Suggested order for 2.0

1. Decide the name, and plan the migration if renaming.
2. Install queue rewrite.
3. Parallel installs, then single authorization, then auto-update.
4. All-apps view with channel selection.
5. Discover tab.
6. Popover decision and the leftover fixes, as they fit.

Ship the steps as 2.0 betas if they're large. UpdateScout's own appcast can
carry a `sparkle:channel` beta for testers.
