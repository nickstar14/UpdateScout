# 2.0.0 vision: one app for everything that can be updated

Written 28 Oct 2026 on `release/2.0.0`. This mixes Nick's ideas with
suggestions from the planning session. It extends
[2.0.0-plan.md](2.0.0-plan.md) and doesn't replace it. Nothing here is built
yet, and no code has changed.

Layout sketches are in [2.0.0-mockups.html](2.0.0-mockups.html). Open it in a
browser. They are rough sketches, not final design.

**How to read this:** items marked **(Nick)** are Nick's own ideas.
Items marked **(suggested)** are new suggestions. **(decide)** marks a
question that needs an answer before building.

## 1. The product in one sentence

A native Mac app that is UniGetUI and CaskHub in one: it updates and installs
software from every source on the Mac, shows progress for many installs at
once, and asks for the admin password once per batch. **(Nick)**

What already exists and stays:

- The update sections from 1.8.0: Homebrew, Sparkle apps, the App Store,
  macOS updates, drivers and extensions, custom sources, the cask oracle, and
  the leftover and hidden lists. **(Nick: "retain the sections like I have now")**
- The menu bar icon, notifications and the headless background check.
- Safe `state.json` writes shared with the background agent.
- The major-upgrade review sheet and release-track detection.

Where it sits among the competition:

- **UniGetUI** already ships macOS and Linux builds that cover Homebrew, pip,
  npm and others. It is cross-platform, not Mac-native, and doesn't cover
  Sparkle apps, direct installs, drivers or macOS updates.
- **CaskHub** browses and installs Homebrew casks but doesn't manage other
  package types.
- **The gap:** a Mac-native app with Sparkle and direct-install detection, plus
  package managers, plus a store-style Discover tab. **(suggested)**

## 2. Name

All of these were checked against both App Stores, Homebrew casks, GitHub, and
the `.app`, `.com` and `.dev` registries. "Not registered" means the registry
returned "not found", which is a good sign but not a guarantee. **No trademark
search has been done on any of them.**

| Name | Findings |
|---|---|
| **Software Prism** | Nothing on either store or in casks. No GitHub repos. `.app` and `.dev` not registered. `.com` taken. |
| **Pack Prism** | Same result as Software Prism. |
| **Pkg Prism** | Same result, and the `.com` also looks unregistered. Reads like a developer tool. |
| **Update Prism** | Free on `.app`, `.com`, `.io` and `.dev`. Keeps "Update" from UpdateScout. Narrower: it says nothing about installing or discovering. |
| **App Prism** | `.app` and `.dev` free. `.com` and `.io` registered, with no live site. "App" fits poorly once pip, npm and cargo are in. |
| **App Courier** | No store or cask clash. `.app` free, `.com` taken. Says "delivery" more than "discovery". |
| Stack Prism | Avoid. A 1.2k★ browser extension, `setube/stackprism`, already uses the name. |
| **PrismPack** | Weak clashes only: an unrelated real-estate iOS app called "Prism Pack" and a 1★ Minecraft plugin. Nothing in casks. `.app` and `.dev` not registered, `.com` taken. Sounds like a product, and "pack" suggests everything bundled. (Earlier marked "avoid"; that was too harsh.) |
| PrismSoft | Avoid. Crowded: Prism Software Corp (print and document software, since 1992), several small "Prism Soft" firms in India and France, and three similarly named GitHub orgs. Sounds like a company, not a product. `.app` and `.dev` not registered, `.com` taken. |

**Why Prism:** a prism takes light from many sources and shows it as one clear
spread. Here that is Homebrew, pip, npm, Sparkle and the rest in one view.

**Decision (Nick, 28 Oct 2026): PrismPack.** It's catchy, easy to remember for
non-developers, and "pack" suggests everything gathered in one place. Software
Prism was the plainer runner-up. The migration plan is in
[2.0.0-rename-plan.md](2.0.0-rename-plan.md).

Still to do before committing: a trademark search, a check of who owns the
`.com`, and a re-check of GitHub (it rate-limited some earlier lookups). The
migration plan comes after the name is chosen.

| **Installed** | Everything installed across all sources, searchable. Where channel switching and pinning live. |

## 5. What counts as "updatable": the category catalogue

Each category is a **source plugin**. Today's `UpdateSource` protocol in
`Models.swift` is already the right seam, so this is growth, not a rewrite.
Difficulty reflects how easy it is to list what's outdated and upgrade it from
a command line.

### Already built (1.8.0)

| Category | Notes |
|---|---|
| Homebrew formulae and casks | Via `brew`. |
| Sparkle apps | Appcast feeds, with release tracks. |
| Cask oracle | Offers Homebrew management for direct installs. |
| App Store | Via `mas`. Updates only, never in Discover. |
| macOS updates | Via `softwareupdate`. Updates only, never in Discover. |
| Drivers and extensions | Matched against the cask database. |
| Custom sources | User shell commands. |

### Good candidates for 2.0

| Category | How to detect | Difficulty |
|---|---|---|
| Python tools (pip, pipx, uv tools) | `pip list --outdated --format=json`, `pipx upgrade-all`, `uv tool upgrade` | Easy. Needs care over which Python environment. |
| Node globals (npm, pnpm, bun) | `npm outdated -g --json` | Easy |
| Ruby gems | `gem outdated` | Easy |
| Rust (cargo) | `cargo install-update`, which needs the `cargo-update` tool | Medium |
| Go tools | No built-in "outdated" list | Hard. Probably skip. |
| Runtimes (mise, asdf, nvm, pyenv, rbenv) | `mise outdated` and similar | Medium. Version-manager commands differ. |
| Editor extensions (VS Code, Cursor) | `code --list-extensions --show-versions` plus the marketplace | Medium |
| GitHub releases for apps with no feed | Compare the release tag to the installed version | Medium |
| Homebrew taps and fonts | Casks and formulae already cover most | Easy |

### Later or exploratory

Docker images, Ollama models, conda, Nix, MacPorts, JetBrains plugins,
shell frameworks such as Oh My Zsh, and Xcode command line tools through a
separate path. Each is useful, but each has a different update story, so add
them one at a time based on what Nick actually uses.

**(suggested)** Build the plugin protocol first, then add pip and npm as the
first two new plugins. They are the easiest and they prove the design.

## 6. Architecture

Three source groups feed an install queue with one lane per manager, which
uses an authorization step and then the installers. In words:

1. **Source plugins** detect updates, search, and describe items.
2. **The install queue** holds every item with an explicit state and runs
   them in lanes.
3. **The authorization broker** collects admin rights once per batch.
4. **Installers** run the real commands.

### Source plugin protocol

Extend `UpdateSource` with optional capabilities so a source can opt in to
only what it supports:

- **detect**: what's outdated. (exists today)
- **install**: one item. (exists today)
- **search** and **info**: for Discover.
- **uninstall**: for the Installed tab.
- **channels**: for sources that have them (Sparkle, Homebrew `@beta` casks).
- **needsAdmin**: whether an item will ask for a password, known before it runs.

### Install queue (the first thing to build)

This is the rewrite already listed first in `2.0.0-plan.md`. Replace the single
`cancelRequested` flag, the shared `"install"` process tag and the `"Queued…"`
string with:

- An **install-state enum**: queued, downloading with progress, installing,
  needs admin, failed with an error, done.
- A **Task and process tag per item**, so cancel works on one item.

## 7. Simultaneous updates **(Nick)**

- A **concurrency setting**, 1 to about 8, shown as "At once" in the toolbar.
- **Lanes, not a free-for-all.** Homebrew holds locks, so parallel `brew` calls
  fail. The rule:
  - Run **downloads** in parallel.
  - Run **installs one at a time per manager**: one `brew`, one `npm`, one `pip`
    environment.
  - Sparkle apps and the App Store can run alongside Homebrew.
- **A progress row per item**, with Cancel and Retry.
- A summary line: "Running 6 of 14".

## 8. One credential for a whole batch **(Nick)**

Today a GUI app can't reuse a `sudo -v` cache between runs, and `sudo -A`
prompts on every call, so "Update all" can ask several times.


> **Correction (29 Oct 2026):** option B below does not work for Homebrew, which refuses to run as root and calls `sudo` itself for pkg casks. See section 4.6 of [2.0.0-build-guide.md](2.0.0-build-guide.md) for the current plan: test whether one `sudo -A -v` primes a cache, and otherwise ask Nick about an in-memory broker.

Options, best first:

| Option | What it is | Cost |
|---|---|---|
| **A. Privileged helper** | A background helper registered with `SMAppService`, approved once in System Settings. The app sends it a short list of allowed operations over XPC. | Proper fix. Needs correct signing and an XPC interface. Check what `build-app.sh` does about signing first. |
| **B. One elevated batch script** | Collect every item that needs admin, run them in one elevated script per batch, with one prompt (`with administrator privileges`). | Works now. One prompt per batch, not per item. |
| **C. Flag admin items** | Mark installer-package casks as needing admin and run everything else without sudo. | Cheap. Fewer prompts but not one. |

**Recommendation:** ship **B plus C** in the first 2.0 betas: items that need
admin are marked up front ("Needs admin"), and one prompt covers all of them.
Move to **A** if the helper proves worth the signing work. **(suggested)**

Rules whichever option wins:

- Never store the password. Touch ID through the system dialog is welcome.
- The helper, if built, accepts only a fixed allowlist of operations, never
  arbitrary shell text.
- The mockup shows the pattern: a bar at the bottom, "3 updates need your
  password. Authorize once for this batch."

## 9. Discover **(Nick)**

A CaskHub-style store across as many categories as possible, **excluding the
App Store and macOS updates** (see decision in section 3).

### What each source can supply

| Source | Search | Details | Popularity |
|---|---|---|---|
| Homebrew casks and formulae | `brew search`, `brew info --json=v2` | Name, description, homepage, version | formulae.brew.sh install counts |
| npm | The npm registry search API | Yes | Download counts |
| Rust (crates.io) | crates.io API | Yes | Download counts |
| Ruby gems | RubyGems API | Yes | Download counts |
| Python (PyPI) | **No usable search.** `pip search` is disabled on PyPI. Use exact-name lookup, plus a curated list. | JSON API by exact name | Third-party only |
| Editor extensions | The marketplace API | Yes | Install counts |

This is a real limit: PyPI search needs verifying before promising it. Treat
Python discovery as "curated list plus exact lookup" until that's confirmed.
**(decide)**

### Home layout

- **Search box** at the top, with results from every enabled source and a
  source tag on each result ("cask", "formula", "npm").
- **Category chips**: Apps, Command line, Python, Node, Rust, Ruby, Go,
  Editor extensions, Runtimes, Fonts.
- **Lists**: Popular, Recently added, and each category.
- **Install buttons**, and "Installed" where it already is.

Casks have no categories, so ship a **bundled category mapping** (Browsers,
Developer, Media, Utilities and so on) that can be updated over time. This is
already noted in `2.0.0-plan.md`.

## 10. Channels and the Installed tab

Kept from `2.0.0-plan.md` item 4:

- **Sparkle:** feasible. Feed items carry `sparkle:channel` tags.
- **Homebrew:** channels are separate casks (`firefox@nightly`, `thaw@beta`),
  so switching means uninstall one, install the other.
- **App Store:** no channels.
- Moving from beta to stable is a downgrade. It needs its own action and a
  warning.

**(suggested)** The Installed tab also holds pin and ignore controls, so
auto-update rules have one home.

## 11. Auto-update and rules

From `2.0.0-plan.md` item 3, unchanged:

- Global and per-app on and off, plus a schedule (daily, on launch, weekly).
- Ignore a version, and pin an app.
- A major upgrade never installs automatically: it always goes through the
  review sheet.
- Optional rules such as "Wi-Fi only" and "never update Xcode".

## 12. Suggested order

1. **Pick the name** and write the migration plan.
2. **Install queue rewrite**: the state enum, per-item cancel.
3. **Source plugin protocol**, then **pip and npm** as the first new sources.
4. **Parallel lanes**, then **one authorization per batch** (options B and C).
5. **Window shell**: the sidebar, the Installed tab and the Activity tab.
6. **Discover**, starting with Homebrew, then npm and the other sources.
7. **Channels, auto-update rules, popover decision, leftover fixes.**

Ship the big steps as 2.0 betas using a `sparkle:channel` beta in the app's own
appcast, as noted in `2.0.0-plan.md`.

## 13. Risks and open questions

- **Scope.** Many categories is a lot of surface. Each source needs its own
  tests and its own failure handling. Ship pip and npm first, then judge.
- **Parallel installs and Homebrew locks.** The lane rule above is essential.
- **Admin helper signing.** Option A depends on signing details that haven't
  been checked yet.
- **PyPI discovery** needs verifying.
- **Python environments.** pip needs a rule for which interpreter is
  "the" one. Prefer pipx and uv tools for command-line tools.
- **Item IDs include the install token.** Changing the ID format resets users'
  ignored and notified lists. New sources must follow the existing format.
- **Menu bar managers.** Re-check Thaw behaviour whenever the menu bar label
  changes.
- **The rename itself** is not decided. See section 2.
